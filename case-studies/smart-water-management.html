Smart Water Management & Leakage Detection System

A real-time monitoring platform that pairs an ESP32 microcontroller with flow and pressure sensors to catch leaks early, cut waste, and give building operators a live view of water usage through a Firebase-backed dashboard.

Computer Engineering, NCIT ESP32 · Firebase · IoT ~7 min read
ESP32 Firebase Realtime Database Flow Sensors Embedded C++ IoT

Overview

Undetected leaks are one of the most common and most preventable sources of water loss in both households and institutional buildings — a slow drip behind a wall or a cracked underground pipe can go unnoticed for weeks, wasting thousands of liters and quietly inflating utility bills. This project set out to solve that specific problem with hardware that is cheap enough to deploy at scale: an ESP32 microcontroller reads live data from flow and pressure sensors installed along a water line, applies a simple anomaly-detection rule on-device, and streams both raw readings and flagged events to a Firebase Realtime Database. From there, a web dashboard gives a building manager or homeowner a live picture of consumption and an immediate alert the moment a leak signature appears, rather than waiting for a monthly bill to reveal the problem after the fact.

The guiding design constraint throughout was affordability and reproducibility: every component was chosen to be available off-the-shelf in Nepal, and the total bill of materials for a single monitoring node was kept low enough that the system could realistically be installed at multiple points in a building rather than just one central meter.

System Architecture

The system is organized into three layers that map cleanly onto how the data actually moves: sensing, edge processing, and cloud sync.

1. Sensing Layer

A YF-S201 hall-effect flow sensor sits in-line with the pipe and produces a pulse train whose frequency is proportional to flow rate. A secondary analog pressure transducer monitors line pressure, since a sudden pressure drop combined with continued flow is a much stronger leak signal than flow rate alone. Both sensors feed directly into the ESP32's GPIO and ADC pins.

2. Edge Processing Layer

The ESP32 counts flow pulses over a rolling one-second window to compute instantaneous flow rate (L/min), and maintains a short moving average to smooth out sensor noise. It compares this against two conditions: continuous non-zero flow during hours when the building's schedule says demand should be near zero, and a flow-versus-pressure mismatch that suggests water is escaping outside the expected fixtures. Either condition triggers a local "leak suspected" flag before any data ever leaves the device — this matters because it means the system can still raise a local alarm (a buzzer/LED) even if the Wi-Fi connection is temporarily down.

3. Cloud Sync Layer

When connectivity is available, the ESP32 pushes a timestamped JSON payload (flow rate, pressure, cumulative volume, and the leak flag) to a Firebase Realtime Database node scoped to that device's ID. A lightweight web dashboard subscribes to the same node and updates in real time using Firebase's listener API, so the displayed chart and alert banner change the instant new data arrives — no polling required.

Firebase was chosen over a self-hosted backend specifically because its realtime listener model removes the need to build and maintain a WebSocket server just to get live updates on the dashboard — a meaningful simplification for a project built and maintained by a single student developer.

Technical Challenges Overcome

  • Pulse-counting accuracy under interrupt load: Reading flow-sensor pulses via a naive polling loop dropped counts whenever the ESP32 was busy with Wi-Fi housekeeping. Moving the pulse counter into a hardware interrupt service routine (ISR) that simply increments a volatile counter — with all the actual math done outside the ISR — fixed the undercounting and kept flow readings accurate even under network load.
  • False positives from normal usage spikes: Early versions flagged ordinary events like flushing a toilet or running a washing machine as leaks. This was resolved by tuning the detection window to require sustained anomalous flow over a multi-minute period rather than reacting to any single reading, trading a little detection speed for a large drop in false alarms.
  • Intermittent Wi-Fi in a utility room: Utility rooms and basements — where flow sensors are typically installed — often have poor Wi-Fi coverage. The device was made resilient to this by buffering unsent readings locally and flushing them to Firebase once connectivity returned, so no data was silently lost during a dropout.
  • Power stability for the sensor line: The flow sensor's pulse output was noisy when powered directly from the ESP32's 3.3V rail alongside Wi-Fi transmission spikes. Adding a dedicated LDO regulator and a decoupling capacitor on the sensor's supply line cleaned up the signal considerably.

Key Code / Hardware Components

The core of the on-device leak logic is intentionally simple, since reliability mattered more than sophistication for a device meant to run unattended for months:

volatile uint32_t pulseCount = 0;

void IRAM_ATTR onPulse() {
  pulseCount++;
}

void loop() {
  noInterrupts();
  uint32_t pulses = pulseCount;
  pulseCount = 0;
  interrupts();

  float flowRate = (pulses / CAL_FACTOR); // L/min
  float pressure = readPressureKPa();

  bool leakSuspected =
      (flowRate > IDLE_THRESHOLD && isOffPeakHour()) ||
      (flowRate > 0 && pressure < PRESSURE_DROP_LIMIT);

  pushToFirebase(flowRate, pressure, leakSuspected);
  delay(1000);
}

On the hardware side, the bill of materials centers on an ESP32 DevKit board, a YF-S201 flow sensor, an analog pressure transducer, a buzzer and status LED for local alerting, and a small 3D-printed enclosure to keep the electronics dry near the pipe fittings — a deliberately minimal parts list to keep per-node cost low.

Key Takeaways

Building this system reinforced a lesson that applies well beyond IoT: the most valuable engineering decisions are often about where to put the intelligence, not how much of it to add. Keeping leak detection logic on the ESP32 itself, rather than deferring every decision to the cloud, meant the system stayed useful even during network outages — which, ironically, is exactly when a physical fault like a leak is most likely to also be unmonitored. It also sharpened my sense of how much noise real-world sensors produce compared to a datasheet's ideal curve, and why buffering and averaging strategies are not optional polish but core requirements for anything meant to run unattended. Finally, choosing Firebase's realtime listeners over a custom backend was a reminder that picking the right managed service can save weeks of infrastructure work that has nothing to do with the actual problem being solved.
